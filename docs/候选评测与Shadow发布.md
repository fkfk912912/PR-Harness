# 候选评测、Shadow 试运行与确认发布

更新代码后重启后端，再刷新浏览器，打开「演进实验室」。数据库启动时自动增加发布字段，保留已有候选、反馈和任务。仅刷新浏览器无法让旧后端加载新增接口。

## 页面上先看哪里

- **正式使用**：后续新建的正常审查任务实际选择的版本；没有激活版本时显示「内置默认策略」。
- **Shadow / 发布状态**：当前候选是否试运行、停止、正式启用或回退。
- **候选版本**：点击历史记录，查看该次回放的基准、Validation / Holdout 分项成绩、门禁、提示词改动及运行配置。
- **真实 Shadow 对照**：显示已完成样本数、候选执行异常、结论存在差异的任务数、双方 Token / 耗时，并链接到具体任务。

评测历史和发布状态分别保存。例如，V7 的历史评测决定仍可以是 `shadow_ready`，顶部「正式使用」已显示 V7；这表示它当时通过评测，之后经确认发布。

## 从生成到使用

1. 在任务中心提交有依据的误报、漏报或坏修复反馈。
2. 点击「从反馈生成候选」，或展开手动提交表单，提交候选提示词。
3. 页面发出的两种候选请求均使用 `activation_policy: shadow`。即使规则分支生成候选，评测通过后也先等待确认。
4. 点击候选，核对改动、回放基准、门禁和分项指标。未通过评测的候选不能通过新发布入口启用。当前正式版本与候选回放基准不同，也需要重新评测。
5. 点击「确认开始 Shadow」，设置抽样比例、样本目标和错误 / 差异门槛，再在对话框确认。候选将对抽中的**新建请求**额外执行完整多 Agent 审查，增加模型调用及 Token。
6. 在「发起审查」提交新任务，或由 GitHub Webhook 创建新任务。正式报告仍使用基准版本；影子结果作为独立任务保存，不回评到 GitHub，也不写入正式 Agent 记忆。
7. 页面在试运行期间每 6 秒刷新。打开双方任务或具体 Finding，结合代码判断质量。仅等待、刷新页面不会生成样本。
8. 点击「确认启用 V…」并再次确认，新建正常任务开始使用候选。也可以在评测通过后直接确认启用；对话框会说明尚无影子样本。
9. 在任务中心查看任务上方的版本提示，以及 JSON 中的 `input.prompt_version`。`input.source: shadow` 表示影子候选任务。
10. 发布后可点击「回退到 …」。首次从默认策略升级也能恢复默认策略，不需要随意激活某个被拒绝的版本。

已创建的任务固定原版本，不因启用、回退而改变。确认窗口取消时不执行操作。后端会检查页面看到的正式版本和试运行批次，拒绝过期页面提交的操作。

## 自动启用与停止

「达到样本目标且错误率、差异比例达标后，授权自动启用」默认关闭。关闭时，达到目标也继续等待人工确认；开启并确认后，系统可以自动将候选设为正式版本，并实际用于新任务。

- 执行错误率 = 候选异常样本数 / 已完成影子样本数。任务失败、模型调用失败、Worker 失败都会计入，不能仅凭任务 `SUCCESS` 判断无异常。
- 结论差异任务比例 = 至少一项问题身份、位置或严重程度存在差异的任务数 / 已完成影子样本数。
- 达到最小样本数后，执行错误率超预算会停止试运行，正式任务保留基准版本。
- 差异不等于错误：候选发现真实漏报也会产生差异，须人工判断准确性。这里的错误预算不统计业务误报率。
- 停止试运行后不再为新请求创建影子任务；已开始的任务可以完成，但不会推动已停止或已替换批次的自动发布。
- 同一次对照只计数一次；旧批次的迟到任务不会计入新批次，即使候选版本号相同。

提示词离线回放当前评测单个 LLM 审查器；Shadow 执行完整 Lead / Workers / Critic 链路。小题库单次满分不构成真实 PR 效果结论。

## 接口与持久化

`GET /v1/evolution/console` 返回实际正式版本、发布状态、候选详情、当前批次对照记录及操作权限。

`POST /v1/evolution/releases` 需要管理权限。请求示例：

```json
{
  "action": "shadow",
  "version": 7,
  "confirmed": true,
  "expected_current_version": null,
  "expected_release_id": null,
  "shadow_percent": 100,
  "min_samples": 5,
  "max_error_rate": 0.1,
  "max_disagreement_rate": 0.2,
  "auto_promote": false
}
```

`action` 支持 `shadow`、`activate`、`stop`、`rollback`。预期版本和批次应来自最近一次 GET，不能长期复用示例中的 null。所有操作进入审计日志。

`skill_versions` / `evolution_runs` 保存候选和离线评测；`deployments` 保存正式 / 候选版本、上一版本、批次和统计；`release_observations` 保存双方结论、Token、耗时和任务链接。SQLite、PostgreSQL 使用相同的发布事务实现。

原有 `/v1/evolution/propose` 的默认激活策略保持 API 兼容。需要等待确认的客户端应显式传 `activation_policy: shadow`。旧版直接激活接口仍是低层管理接口；新 GUI 使用带门禁、确认及过期状态检查的发布入口。

## 回归验证

```powershell
.\.venv\Scripts\python.exe -B -m unittest discover -s tests -v
```

安装开发用 Playwright 后，可运行 `node tests/evolution_ui.cjs`。脚本自动启动临时数据库和假模型服务，验证历史选择、确认取消、真实 Shadow 任务执行、手动 / 自动启用、回退和移动布局；不会使用工作区数据库或模型凭据。Playwright 可通过 `PLAYWRIGHT_MODULE` 指定模块路径，浏览器可通过 `PLAYWRIGHT_CHANNEL` 指定。截图和结果写入已忽略的 `validation/evolution-ui/`。
